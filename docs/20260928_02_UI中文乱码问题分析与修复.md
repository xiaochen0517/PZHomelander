# 20260928_02 UI 中文乱码问题分析与修复

## 问题现象

设置窗口（`SettingsWindow.lua`）中：

- 标题里的英文部分（`Homelander`）显示正常，紧跟着的中文「属性锁定设置」显示为乱码 `^'n`
- 启用/禁用切换按钮的中文「已启用」「已关闭」分别显示为 `s`、`/(` 这类无意义符号

## 原因分析

### 不是字体缺字形（tofu）问题

如果单纯是当前字体的字形表里没有对应中文字形，通常表现为空白方块（tofu）或完全不显示，而不会出现看起来像是某种"随机 ASCII 符号"的输出。这里"一串中文变成一两个不相关的 ASCII 符号"是典型的**编码误判（mojibake）**特征：多字节 UTF-8 序列被按单字节编码（如 Latin-1/CP1252 或引擎内部按字节读取）逐字节解释，大部分字节因落在不可打印/不可映射范围而被跳过或不显示，少数字节恰好落在可打印范围内，就显示成了看似无关的符号。

### 根因：PZ 的 Lua 脚本加载器（Kahlua2）对源码内联的多字节 UTF-8 字符串处理不可靠

Project Zomboid 使用 Kahlua2（一个 Java 实现的 Lua 解释器）加载 `.lua` 脚本。它在读取脚本源码、构造字符串常量时的编码处理路径，和游戏本体的本地化文本加载路径（`Translate`/`getText()` 体系，读取 `media/lua/shared/Translate/<语言>/UI_*.txt`）是两套不同的代码路径。后者是专门为多语言支持设计的，会显式按 UTF-8 解码；而直接写在普通 `.lua` 文件里的字符串字面量，遇到中文这类多字节 UTF-8 字符时，历史上就存在解码不一致的问题，是许多中文 PZ Mod 作者踩过的坑——这也是为什么"正规"的中文本地化做法是把展示文本放进 `Translate` 目录下的语言文件，而不是直接嵌在逻辑代码的字符串字面量里。

本 Mod 的 `SettingsWindow.lua`/`StatLocks.lua` 里的中文标签、按钮文字都是直接写在普通 `.lua` 源码里的字符串字面量，命中了这个问题。

### 是否是"多语言适配"问题

是，但准确说法是：**这不是字体/字形的多语言适配问题，而是文本加载路径的多语言适配问题**。PZ 原生支持中文显示（游戏本体切换到中文语言时菜单、物品名都能正常显示中文），但走的是它自己的 `Translate` 本地化文件体系；普通 Mod 逻辑代码里的内联字符串字面量并不在这套体系内，所以不能假设"文件保存成 UTF-8 就万事大吉"。

## 修复方案

`Translate` 体系需要额外建立语言文件、按 key 取文本，对于一个"简单实现、不过度设计"的小工具 Mod 来说增加了不必要的复杂度和新的（未在反编译源码中验证过的）API 使用面。按照约定的备选方案——**直接改为纯英文实现**，彻底绕开这个编码问题，本次改动：

- `shared/Homelander/StatLocks.lua`：5 项状态的 `label` 从中文改为英文（`Health`/`Overall Health`/`Hunger`/`Thirst`/`Fatigue`），日志提示改为英文
- `client/Homelander/UI/SettingsWindow.lua`：窗口标题改为 `Homelander Stat Lock Settings`，方向标签 `MODE_LABEL` 改为 `At Least`/`At Most`，启用/禁用按钮文字改为 `ON`/`OFF`

代码注释仍保留中文（注释不会被引擎解析为运行时字符串、不会被 `drawText` 渲染，不受此问题影响，不影响可维护性）。

## 结论

- 乱码原因：Kahlua2 加载普通 `.lua` 源码时，字符串字面量中的多字节 UTF-8 中文没有被正确解码，本质是"文本走了错误的加载路径"，而非字体缺字形
- 正规修复需要接入 PZ 的 `Translate` 本地化文件体系，但会引入新的复杂度和未验证 API
- 按照"简单实现"的原则，选择直接把运行时 UI 文本改为纯英文，规避整个问题
