# 属性锁定 / 免死 功能实现方案分析（供审查）

> 基于 `PZ_健康死亡系统API说明.md` 的分析结论。本文仅列方案与取舍，不包含具体实现代码，供决策后再落地。

## 0. 能力边界前提

PZ Build 42 Mod 是纯 Lua 环境，没有正式的 Java 字节码修改 API。可用手段只有：

1. **事件回调**（`OnPlayerUpdate`、`OnPlayerGetDamage`、`OnWeaponHitCharacter` 等，仅通知，不能改变已发生的行为）；
2. **钩子**（`LuaHookManager` 的 `WeaponHitCharacter` 等少数几个，回调返回 `true` 可**取消**本次行为）；
3. **反射调用暴露类的 public getter/setter**（`IsoGameCharacter`/`BodyDamage`/`BodyPart`/`Stats` 等）。

关键限制：游戏内部（Java 侧）逻辑之间互相调用**不经过 Lua 反射层**，所以"覆盖 Lua 可见的 setter"只能拦截**其它 Lua 代码**对该值的写入，拦截不了游戏自身每 tick 的内部改动。凡是要锁住一个会被游戏自身逻辑持续修改的数值，唯一可靠手段是**每 tick 事后强制纠正**（下文方案 A 系列）。

---

## 一、属性锁定（数值恒定不变）

**方案 A（推荐）：`OnPlayerUpdate` 每 tick 强制赋值**

- 做法：每 tick 读取目标属性当前值与预设锁定值比较，不等则强制写回。
- 优点：实现简单统一，对 `Stats` 里任意属性（饥饿/口渴/疲劳/压力/体温…）和 `health`/`overallBodyHealth` 都适用。
- 缺点/注意：
  - 存在"游戏改了 → 下一 tick 才纠正"的一帧滞后，一般不可感知。
  - `overallBodyHealth` 是每 tick 由各 `BodyPart.health` **重新汇总计算**得出的（见 `BodyDamage.calculateOverallHealth()`），只锁 `overallBodyHealth` 本身会被下一次汇总覆盖，**必须连同锁定每个 `BodyPart.health`**（或锁定其上游输入，如体温/饥饿等级）才能真正锁死总健康值。

**方案 B：覆盖 Lua 侧 setter（monkey-patch）**

- 做法：替换 Kahlua 反射注册的方法表条目，拦截对某属性的赋值调用。
- 结论：**不适用于本需求**。游戏自身对属性的持续修改是纯 Java 内部调用，不经过这层，覆盖了也拦不住；仅在"防止其它 Mod 或本 Mod 自身代码误改"的场景下有意义，可作为方案 A 的补充加固，不能替代。

**建议**：采用方案 A。

---

## 二、最小值锁定（不可低于指定值）

**方案 A（推荐）：`OnPlayerUpdate` 每 tick 下限纠正**

- 做法：每 tick 检查 `value < floor` 时才纠正为 `floor`，高于阈值时不干预，保留数值在阈值以上的正常波动。
- 优点：对游戏体验破坏最小（例如"血量不低于 30"，30~100 区间的正常起伏依然生效）。
- 缺点：同属性锁定，存在一 tick 的纠正窗口；`overallBodyHealth` 同样要连同各 `BodyPart.health` 一起兜底（否则汇总值仍可能被算低于阈值一瞬，等下一 tick 才纠正回来，属正常滞后，不算漏判）。

**方案 B：仅在相关事件内纠正（性能优化型）**

- 做法：不逐 tick 轮询,只在 `OnPlayerGetDamage` 等"数值确实发生变化"的事件回调里做下限检查。
- 优点：开销更低。
- 缺点：必须覆盖**全部**可能导致该值下降的路径；若遗漏某条隐藏路径（例如未触发标准事件的特殊扣血分支）会漏判。目前已确认的扣血事件覆盖饥饿/口渴/中毒/流血/感染/负重/武器命中，基本完整，但不保证是全集。
- **建议**：可作为方案 A 的性能优化叠加使用（关键事件即时纠正 + 低频 tick 兜底），而非单独使用。

---

## 三、可以受伤，不可死亡

三个需求中**实现难度最高**的一个：PZ 的死亡判定里，**战斗类伤害**（武器命中、载具撞击）是在同一次 Java 调用栈中**同步**完成"扣血 → 判死 → 处刑"的，中间没有 Lua tick 的插入空间；而**生理类伤害**（饥饿/口渴/感染/体温/流血）的扣血与死亡判定是分离的两步，中间有一次 tick 的窗口可利用。需要分来源处理：

### 3.1 武器命中（近战/远程）—— 有可靠的前置拦截点

反编译确认 `IsoGameCharacter.Hit()` 在真正扣血前会先：

```
触发事件 OnWeaponHitCharacter(wielder, target, weapon, damageSplit)
触发钩子 WeaponHitCharacter → 若回调返回 true，直接 0 伤害，流程终止
```

- **方案 A（推荐）**：注册 `WeaponHitCharacter` 钩子，回调中判断"若本次伤害会导致目标死亡"就返回 `true` 取消本次命中（相当于该击完全被格挡/无效）；否则放行，伤害正常生效。可以做到"平时正常掉血，只在致命一击上兜底"。
- **方案 B（备选，兼容性更好）**：改用普通事件 `OnWeaponHitCharacter`（而非 Hook API），回调内同步调用 `target:setAvoidDamage(true)`。因为事件回调在 Java 侧是同步执行完才继续往下走，执行到 `avoidDamage` 检查时该标志已生效，效果等同方案 A，但用的是更通用的 Event 接口而非专门的 Hook 系统，长期兼容性通常更好。
- 覆盖范围：仅武器命中路径。

### 3.2 载具撞击 / 摔落等瞬时伤害 —— 没有可用的取消点

反编译确认 `applyDamageFromVehicleHit()` 路径中**没有任何 Lua 事件或钩子**，只受 `isGodMod()` 的 Java 内部判断保护，扣血后立即在同一调用里同步判 `isDead()` 并 `Kill()`。这意味着：

- 纯 Lua 方案在此路径上**存在理论上的绕过窗口**：一次瞬间超高伤害（如高速撞击、摔落）可能在同一次调用内把血量直接打到 0 并处刑，而 Lua 侧完全没有插入纠正的机会。
- 可选缓解：
  - **方案 A**：叠加"最小值锁定"（第二节方案），把 `health`/`overallBodyHealth` 常态维持在较高安全值（例如从不低于 30），降低"单次伤害超过剩余血量"的概率，但不能从原理上杜绝——伤害数值仍可能一次性超过安全垫。
  - **方案 B（更彻底但代价大）**：Java 层字节码注入（如通过 ASM/Javassist 编写 Java Agent，在游戏启动时挂钩 `applyDamageFromVehicleHit`/`hitConsequences`），从源头拦截。优点是**完全可靠、无时序窗口**；缺点是脱离了标准 Lua Mod 的分发方式（需要自定义启动参数/独立安装步骤，无法直接通过创意工坊分发），且强依赖游戏内部实现细节，**版本更新极易失效**，维护成本高。**不建议**作为首选方案，仅在实测发现纯 Lua 方案确有明显漏判且无法接受时才考虑。

### 3.3 生理伤害（饥饿/口渴/感染/体温/流血）—— 用"最小值锁定"兜底即可

- 扣血（`BodyDamage.Update()`）与死亡执行（`PlayerOnGroundState` 检查 `isDead()` 后调用 `die()`）分属两个独立步骤，中间存在至少一次 tick 的窗口。
- **方案（推荐）**：直接复用第二节的"最小值锁定"方案，在 `OnPlayerUpdate` 中把 `health` 与 `overallBodyHealth`（连同各 `BodyPart.health`）钳制在一个安全阈值以上（建议不要卡在刚好 >0，考虑浮点误差和同 tick 内可能的后续扣血，建议留一定余量，如 ≥1.0/100）。
- 冻死分支（`BodyDamage` 中直接对 `health` 赋 0 的特殊分支）同样发生在 `Update()` 内部、`die()` 执行之前，只要纠正逻辑在其后执行即可覆盖，无需特殊处理。

---

## 四、总体建议

1. **优先落地纯 Lua 方案**：武器命中用钩子/事件取消（3.1），生理伤害用最小值锁定兜底（3.3）。这条路径符合 PZ Mod 生态、可正常上传创意工坊、对游戏更新的适应性也最好。
2. **载具/摔落属于已知的理论薄弱点**（3.2），建议先按方案 A 加安全垫上线，再通过实测（高速撞车、高处摔落等边界场景）验证实际发生概率；如果实测中此类死亡确实发生且不可接受，再评估是否要上 Java 字节码注入这种更重的方案。
3. **不建议**一开始就采用 Java Agent/字节码注入方案：维护成本、分发方式、版本兼容性三方面都明显劣于纯 Lua 方案，只应作为"实测证明纯 Lua 不够用"时的补救手段。
